# Social cues (research prototype) - status, limits and demo checklist

Status date: 2026-10-21. Branch `dev/training-oc-additional-20261019-a`. Labels: **[V]** verified in this repo or in a receipt, **[I]** inference or design choice, **[U]** unknown / not verified. **[V, secondary summary]** (section 7) means only that a summarised page reading reported the text; it was not re-checked against the primary source. This is not legal advice.

## 1. What this is, and what it is not

1. **A research prototype.** It looks at observable head, expression and (behind the same research flag, when optional pose landmarks exist) upper-body movement over a few seconds and reports hedged "signs consistent with ..." hypotheses: `nervous-like`, `unsure-like`, `needs-help-like`.
2. **The Stage 1 logic is HB-1, a hand-written heuristic baseline** (`socialcue/state.py`, frozen config `socialcue/hb1_config.json`, canonical sha256 `4940a4cbbb1df3c2af27407e78546e47812c5134b8fcc2aec0daad9e2874b6b3`). Every threshold is a hypothesis chosen by the designer and was **never tuned on real data**. Its confidence is capped at 0.8 and it abstains often ("No cue / insufficient evidence" is the expected default).
3. **It is NOT a validated reader of feelings.** No accuracy, sensitivity, base rate or real-world efficacy exists for any of the three states. Do not quote one.
4. **Label validity.** The three states cannot be validated on acted basic-emotion corpora such as RAVDESS or CREMA-D: acted affect is not nervousness, uncertainty or need for help [I]. Facial and bodily movements do not map reliably to inner states (Barrett, Adolphs, Marsella, Martinez and Pollak 2019, *Psychological Science in the Public Interest* 20(1):1-68, doi 10.1177/1529100619832930 [V, research receipt section D]). "Gaze" in this prototype is only a **head-orientation proxy** (eye-midpoint to nose offset); the five-point landmarks contain no pupils.
5. **Not for decisions about people.** See `docs/ETHICS.md`. Never point it at staff, students or job candidates (section 8).

## 3. Using the flagged API and the panel

Nothing below is on by default. The default `/api/infer` response schema is unchanged. Continuous valid single-caller JPEG/MPO/PNG requests with one admitted session id preserve the 36df602 default body/fusion sequence, including zero, two and intermittent detected faces (synthetic before/after oracle). Anonymous requests cannot safely retain temporal identity: they now use no retained movement history, so with an optional visible pose their legacy body/fusion can differ after the old warm-up interval. With the currently absent pose model the default response is unchanged [V, synthetic tests].

**API** (`backend/app/main.py`, `backend/app/socialcue_session.py`):
- Add the query flag `socialcue=1` to `POST /api/infer`. Only the exact value `1` enables it; any other or malformed value behaves as `0` (no 422).
- Send a client-generated, high-entropy **session id in the header `X-Socialcue-Session`** (22-64 characters of `A-Za-z0-9_-`, e.g. `crypto.randomUUID()`). Ids are bearer secrets. Without a valid id nothing is stored and the block reports insufficient evidence (`no_session_id` / `invalid_session_id`).
- The response gains an additive `socialcue` block: `states`, `insufficient {flag, reasons}`, `window`, `heuristic: "HB-1 hypothesis, unvalidated"`, `proxy_eval_ref: null`, and a research `banner`. More than one face gives `multiple_faces` and no state. Any internal failure gives `internal_error` with HTTP 200, never a 500 from the cue path.
- Stage 2: with valid session id and 33-landmark optional estimator output, `socialcue.body` reports descriptive cues and `states[*].body_support` records bounded support for existing HB-1 states only. Cue confidence is capped at 0.6 (0.3 when face/bystander matching is unchecked), the delta clamp is [-0.05, +0.10] (a safety rail: under the frozen weights the largest reachable positive delta is +0.0375 for nervous-like and +0.015 for the other two states; the weak negative is -0.05 checked, -0.025 unchecked), and final HB-1 confidence at 0.8. Insufficient HB-1 evidence is never rescued. An explicit absent-estimator marker means `body.status=unavailable`, `reason=no_pose_model`; a working estimator with `visible=False`, empty/missing landmarks, or quality at/below the legacy 0.3 visibility threshold yields `pose_not_visible`; malformed landmark/quality payloads yield `invalid_pose_payload`. Each case appends no pose frame and resets only that session's body history, preserving face history and other sessions; removing the body block leaves the exact HB-1 result, without added support fields or score rounding. The legacy top-level response is unchanged without the flag.
- Pose frames contain only copied 33x3 numeric landmarks, image dimensions, same-frame face count/box and the same server monotonic instant as the face record, never client timestamps or images. They share the 64-frame count cap / 8-session / lazy 60-second TTL and DELETE lifecycle; face records additionally use the S56 binned eight-second history, while pose timestamps/ring remain per-request; absent pose/subject, multi-face or changed image size resets body history. The legacy 30-frame movement ring is now keyed by the same admitted header id (including default/unflagged requests carrying a valid id), with the same eight-session LRU, lazy 60-second TTL, absence/size/discontinuity reset and DELETE clearing. Anonymous/invalid-id requests never accumulate movement across requests. Numeric landmarks and legacy movement are not shared across ids. Face count gates only Stage-2 poses and HB-1 cues, not the legacy movement/fusion fallback. Absent pose, size change and shoulder discontinuity still reset legacy warm-up. They are heuristics, not identity verification. A bearer id is still not authentication. Nothing is logged or written to disk. A body-extraction/attachment exception reports body `internal_error` while preserving the already computed HB-1 result (HTTP 200). Estimator timestamps are never read. A valid bearer session id is the backend's proxy for the existing panel consent gate, **not authenticated body consent**; callers can manufacture ids. No real body capture/model installation is authorized. The panel shows an optional body-evidence status line; it adds no separate body consent.
- `DELETE /api/socialcue/session` with the same header drops that session. It is unauthenticated; the id is the only secret.

**Panel** (`frontend/src/SocialCuePanel.tsx`):
- Hidden unless the dashboard URL carries `?socialcues=1`.
- **Consent gate**: the live camera cannot start until the checkbox "I am the only person in view and I agree to send camera frames to the configured local backend for this research prototype. Stop or unchecking this box ends capture. Read the capture notice for retention limits." is ticked. Stop, revoking, or a failed start resets the consent, aborts the in-flight request, stops all tracks owned by the current camera epoch and clears the display; pending older grants are invalidated and all their tracks are stopped immediately on arrival without ever being published. Stale controller continuations cannot close a newer camera. Stop and revoke send `DELETE /api/socialcue/session` **only if at least one frame was already sent** for that session (pressing Stop before the first frame sends no DELETE). The loop sends about 8 frames per second with exactly one request in flight, and pauses while the tab is hidden. Capture ownership is independent of request health: during recoverable request errors Stop and consent revoke remain available, and demo selection is disabled and refused by its handler. Responses begun before a hide are discarded after frame/fetch/JSON awaits, even after resume (generation and pause epoch checks). Visibility changes while the camera is still opening are remembered: a hidden tab begins paused with no frame timer or POST, and resumes only after becoming visible. Stop/revoke remain available while paused; the camera stream can remain open until Stop.
- **Demo (no camera)**: a selector with seven fixed synthetic scenarios (calm, nervous-like, unsure-like, needs-help-like escalation, insufficient, multi-person, dropout), labelled "SYNTHETIC DEMO - fabricated values, no camera and no request". It sends nothing; entering demo is refused while a live controller owns capture or is starting.
- The panel shows three rows with a confidence bar on a 0-0.8 scale and a "Why" list of contributing features. Multi-person always reads "More than one person in view: not analysed".

For ordinary unpaced streams, temporal support uses at most one credit per expected 8-FPS time bin, anchored to the newest usable record in the rolling window (the S56 paced API uses its fixed session origin, described below); exact duplicate capture instants are coalesced, preserving unusable or multi-person evidence. Credits are limited to occupied bins, but this does not guarantee minimum spacing: frames about 1 ms apart straddling a bin edge can earn two credits for one tight cluster (bounded at 2x per such cluster). This requires millisecond phase alignment. S24 observed it only in constructed synthetic timing probes, not in real capture: no real capture has been run. A minimum-spacing definition is the proposed alternative to assess before any calibration; it is not implemented here. For unpaced streams coverage still credits distinct 125 ms bins anchored at the newest usable record; paced API retention and coverage share the fixed session origin. A trailing absent tick cannot shift those bin edges while the usable set is unchanged; elapsed span/denominator and window membership still change with time, so support can age out normally. Boundary/bursty sampling remains sensitive to usable-record timing (a new usable record can shift the anchor), not validated timing robustness. Stage-2 self-touch uses observed contiguous first-to-last contact time, splitting at nonpositive dt or dt above the frozen `max_pair_dt_s`; no extra median-frame duration is credited. Since S21 the >=0.5 s condition needs 0.5 s of observed contact: four observations at 8 FPS span 0.375 s and no longer qualify (they were previously credited as 0.5 s). This is a sensitivity/feature-definition change despite unchanged thresholds; the BODY config hash cannot detect code-level definition changes. Stage-2 coverage remains a frame/pair-count fraction, **not a fraction of elapsed time** (bursty stillness windows can still have high pair coverage). Body evidence requires a strict Python `int` face count (excluding `bool`): `1.0` and numpy integer scalars are `invalid_input`; callers must validate and cast first. Integer zero is `no_subject`, negative/malformed values are `invalid_input`, and integers greater than one are `multiple_people`; only integer 1 admits evidence. Stage 2 is wired behind the research flag; no pose model is installed or loaded by this change, and explicitly absent-estimator output yields `socialcue.body.status=unavailable`, `reason=no_pose_model`; working-estimator invisible/empty output yields `pose_not_visible`, malformed payloads yield `invalid_pose_payload`. HB-1 output remains unchanged in these cases.

`window.fps` keeps its existing output key for compatibility but means **bin-credit rate per second**, not measured usable FPS: occupied expected-time bins divided by the window span. `usable_frames` counts usable distinct instants; coverage credits distinct 125 ms bins. A 10-FPS synthetic stream can thus report 30 usable frames but `fps=8.28` (formerly 10.34). Jitter can put two observations in one bin, reducing coverage and coverage-scaled confidence relative to perfect-timing synthetic streams. With the former evaluation-time anchor, the S22 independent review's **synthetic 200-seed timing probes** found that uniform 90-160 ms spacing changed mean coverage 0.995 -> 0.933 (minimum 0.917 -> 0.792); 60-190 ms spacing changed mean 0.984 -> 0.889. Insufficiency rates did not change in those probes. Those figures predate the S23 newest-usable anchor and are historical synthetic timing effects, not measurements of the new anchor or observed camera measurements: live confidence may run a few percent below perfect-timing synthetic streams, and needs calibration/validation before any real run. Frozen thresholds were not changed.

Pause and recoverable request errors clear the displayed active cue rows, confidence and evidence as well as the live announcement. Visibility is sampled once on mount, so an already-hidden mount starts paused. **Limitation:** no request timeout: a never-settling dependency can stall resume (or restart), because the single in-flight tick remains owned until its promise settles; Abort is cooperative. DELETE advances a per-id generation; HTTP captures a read-only pre-upload snapshot and registers only after an inference slot is available. Stale work cannot append/recreate the deleted entry and is refused with HTTP 409. The admission/tombstone map is bounded to 128 ids; eviction invalidates old tokens rather than accepting them. DELETE also invalidates a pending upload when no current entry exists. This is not process cancellation, physical memory erasure, or erasure of a response already delivered; a NEW post-DELETE request with the same bearer id is a new admission and may create a new entry. No real browser/camera behavior has been verified.

### Primary dashboard movement session (S39)

The ordinary dashboard (`frontend/src/App.tsx`, separate from SocialCuePanel) now sends `X-Socialcue-Session` on every live infer request. It creates one cryptographic random id on first live Start for that mounted page, retains it only in a React ref across control changes/restarts, and never stores it in browser persistence. A new page instance gets a new id; no secure random source means capture fails closed. This restores the dashboard body/fusion history without a shared anonymous fallback. The linked pre-Start notice makes live Start an opt-in to at most 30 numeric movement frames in backend memory. The same global eight-session LRU / lazy 60-second TTL applies to flagged AND unflagged valid-header traffic. The primary dashboard does not send DELETE on Stop: Stop ends capture/requests, while numeric history can remain until idle expiry/access or backend exit. SocialCuePanel retains its separate consent/session/DELETE behavior. Demo sends no request and retains no backend history. A header is a bearer context, not authentication or proof of third-party consent; public CORS and id-flood availability limits remain. Anonymous callers still have no retained temporal history.

### S56 correctness definitions (review S53; synthetic evidence only)

- `analyze(records, evaluation_time=None)` retains last-record timing for ordinary inputs. An explicit finite endpoint evaluates support on **(t-W, t]**, with the left endpoint excluded and right endpoint included, while retaining earlier records for dwell and sustained evidence. Pilot `_hb_windows` now passes every scheduled endpoint explicitly, so empty intervals age into abstention instead of repeating stale positives. Annotation-overlap assignment is otherwise unchanged.
- **Head-jitter feature DEFINITION changed under the unchanged HB-1 config hash** `4940a4cbbb1df3c2af27407e78546e47812c5134b8fcc2aec0daad9e2874b6b3`: roll is the **directed eye_R-to-eye_L angle**, period 2*pi; a pi eye-order reversal is not declared the same directed orientation. S65 unwraps broad distributions about their circular mean, with sorted accurate summation for order independence. A sample range <= pi uses the identical plain-SD arithmetic. Near-zero circular resultants use a deterministic zero-angle cut. The circular-mean unwrap is continuous where the circular resultant is well away from zero, but can still jump when the resultant is small but nonzero, beyond the zero-cut fallback threshold. In the S66 reviewer's executed synthetic example, a 4e-16 move changed SD from 2.13 to 1.58 at |R|=0.0034; these balanced wide samples already saturate the jitter margin. This is a residual discontinuity, not a global continuity guarantee (S67, 2026-10-21). The review boundary/orderings and the near-branch-cut regression are tested. This removes artificial near-2*pi jitter for almost constant eye-lines; thresholds were not tuned. A 444-case old-source comparison covers all seven standard scenarios across strengths, seeds and prefixes; this is synthetic compatibility evidence, not real-camera validation. The config hash identifies thresholds/configuration, **not feature implementation**.
- The session face ring keeps **one representative per 125 ms bin**, using the first session instant as a fixed origin shared by retention and `PacedRecords` coverage. Within one bin multi-face records win first, then a usable record beats an unusable tick (the full stream would still credit that bin), and ties keep the latest multi-face record but the earliest other record (S65 prevents a later same-bin multi-face instant from disappearing prematurely at the rolling left edge; S56b replaced an earlier adverse-first order in which a same-bin no-face tick erased the usable credit). Fixed origin prevents high-rate arrivals from sliding the newest bin indefinitely and erasing warm-up. At most 64 face records and the latest eight seconds remain; TTL/LRU/DELETE also discard the origin. Ordinary unpaced lists keep the historical newest-usable coverage anchor. This API sampling/coverage definition can change confidence relative to dense raw input; there is no claim of dense-stream confidence equality. Because the ring keeps the LATEST multi-face tick of a bin, an explicit evaluation endpoint inside a same-bin multi-face cluster and before that retained tick can miss an earlier multi-face tick that the full stream sees. The S66 reviewer's synthetic sweep found 88 mismatches in 340 such endpoint cases; ring and full stream agreed for endpoints at or after the cluster (0 mismatches in 2,370 reviewed cases). The HTTP path evaluates at the newest retained record and cannot hit this earlier-endpoint case. Keeping both the earliest presence and the latest multi-face instant is the known alternative, not implemented. Latest multi-face replacement can also shorten dwell. These are synthetic retention trade-offs, not real-stream equivalence evidence (S67, 2026-10-21). A representative can lag a same-bin arrival by less than 125 ms. Strict dwell >5 s stays strict (no escalation at exactly 5 s); any first post-boundary escalation can wait for the next retained bin. Manufactured full-stream versus ring comparisons cover 8, 9, 13, 16, 20, 30 and 60 fps, including the exact boundary and settled post-boundary state; at extreme rates (240 fps tested for bounds only) one-in-N binning can alias with a frame-index-driven synthetic label cycle, so ring and dense-stream states are not claimed equal there. Retention is also trimmed to the latest eight seconds at low request rates. The raw 64-pose and 30-movement rings are unchanged; no extra frame buffer or unbounded dwell state was added.
- **Pilot scheduling bound (S58):** `_hb_windows` keeps the dense one-endpoint-per-second schedule for ordinary streams (at most `MAX_DENSE_ENDPOINTS` = 20000 endpoints, results byte-identical to before). A stream spanning more endpoints (for example one stray record at t=1e6) uses a bounded sparse schedule instead: endpoints whose window holds at least one record, plus endpoints inside the alignment reach of an annotated block (emitted, and abstaining when empty); other endpoints cannot align to any block, so scoring is unaffected. Work is bounded by about 3 x records + 4 x blocks.
- **Clock validation (S58, corrected S65):** Every store clock read is validated before purge or any dependent branch, including movement with empty points or anonymous admission. NaN, positive/negative infinity, None, bool and non-numeric values raise `NonFiniteClock` without mutation. `SocialCueSessions.add` (and the legacy movement path) refuses a non-finite or non-numeric clock value, or a record with a non-finite instant, with `NonFiniteClock` before any mutation, so retained history, last-use times and other sessions are untouched; the flagged block reports `internal_error`. Production uses `time.monotonic`; only an injected clock can trigger it.
- First-two-rater agreement uses those two raters' scorable pairs independently of later-rater coverage, including its participant bootstrap. Alpha units include missing ratings as `None` and drop only units with fewer than two usable ratings. Third-only participants do not alter pair counts/CI participant metadata. Existing low-positive interpretation gates and consensus rules are unchanged. Partial/unscorable third-rater tests are manufactured only.

### S60 correctness definitions (review S59; synthetic evidence only, 2026-10-21)

- **F1 fidget energy is a feature-DEFINITION change under the UNCHANGED BODY hash** `c2105b50...` (as for S21 and S56; the hash covers thresholds, not code-level definitions). Hand speed is now measured over a fixed 0.25 s lag (`FIDGET_LAG_S`; the earlier position is interpolated), so independent landmark jitter no longer adds energy in proportion to the frame rate: calm noise (sigma 0.01) reads about 0.09-0.11 at 8, 10, 20 and 30 fps and no longer reads as fidget at 20/30 fps. Limits of the lagged definition (review S61 findings A, B, D; synthetic numbers on the fidget fixture at amplitude 0.08, no real data): displacement over a fixed 0.25 s lag is a comb filter, so it is nulled for motion at multiples of 4 Hz and attenuated near them (20 fps, 4 Hz: energy 0.000, was 1.141; 10 fps, 3 Hz: 0.246, not present, was 0.571; 10 fps, 4 Hz: 0.130, was 0.923). The effective detection bar for real motion at the shipped rate is higher than before: at 2 Hz and 8 fps the energy is 0.32 against the unchanged 0.30 threshold (confidence 0.04), and the fixture amplitude had to be raised 0.06 -> 0.08 to stay above it. Rate-invariance holds for independent landmark noise only; synthetic 2 Hz motion still moves 0.32 -> 0.47 from 8 to 30 fps. body_motion, stillness and freeze_onset still depend on frame rate (calm noise sigma 0.004 body_motion 0.054 at 8 fps, 0.211 at 30 fps; stillness present at 8/10 fps and absent at 20/30 for pure noise), so offline replay above 8 fps is not comparable. No real-motion calibration exists, and the Stage-2 motion definition will be revisited when real pose data exists. Fixture numbers in older receipts (fidget_energy, stillness, body_motion, hand_range) are not comparable with S60 and later. Values are not comparable with earlier receipts. Thresholds are unchanged; the synthetic fidget fixture's default amplitude moved from 0.06 to 0.08 so it still reads present (energy about 0.34 against the 0.30 threshold). A new unavailable reason `too_few_pairs` applies when fewer than `min_pairs` lagged pairs exist. Gesture strokes (F7) keep consecutive-frame speeds. Synthetic only: no real-motion calibration.
- **F3 support maxima:** the largest reachable positive confidence delta is +0.0375 (nervous-like), +0.015 (unsure-like), +0.015 (needs-help-like), exported as `MAX_POSITIVE_SUPPORT`; the +0.10 clamp is never reached. No weights were retuned.
- **F4:** when the bystander check did not run, the weak negative delta is scaled by 0.3/0.6 to -0.025 (note says so); checked it stays -0.05.
- **F5:** pose metadata for the body block comes from the record just added (`PacedRecords.current`), not from the older retained same-bin record. HB-1 evaluation time is unchanged, so HB-1 itself can still lag a same-bin arrival by under 125 ms.
- **F6:** `actor_disjoint_split` uses largest-remainder sizes (floor of 50/25/25 percent, remainders to the largest fractional part, ties to FINAL, then VAL, then DEV; every role at least one). Sizes for some n differ from the earlier rounding (for example 6 actors: 3/1/2, 9 actors: 5/2/2); results for fixed seeds are not comparable with S8-S59 splits.
- **F2:** the adapter sentinel class `excluded` is not a confuser. `confusers[ep]` reports `excluded_n` separately, plus `n_answered`, `n_abstained`, `hb1_positive_n`; `hb1_positive_rate` is hb1_positive_n / n_answered (abstentions excluded) and `abstention_rate` is n_abstained / n_clips. With the synthetic adapters there is no real confuser class, so both rates are null (earlier reports showed 0.0 / 0.4 computed over excluded clips).
- **F7:** `freeze_onset` also needs each half of the window to meet the cue coverage floor (reason `occluded: coverage X (first|last half)`).
- **F8:** fidget needs a median frame interval of at most 0.125 s (8 fps; `min_fps_fidget` in the frozen BODY config, not changed). The shipped client period is 120 ms minus request time, so any median frame interval above 0.125 s makes the fidget cue unavailable (`fps<8`).
- **F9:** the panel shows a specific text for `session_invalidated`. **F10:** `label_agreement` is binary only; complete paired categories must be hashable and, when there are two, include the explicit positive label. Otherwise it refuses with `unhashable_values` or `binary_labels_only`; all agreement statistics use the same normalized complete pairs. Two non-positive categories are never folded together into "absent" (S65).

### Backend request and estimator limits (S35; synthetic-tested only)

- The estimator payload is validated into an immutable 33x3 numeric snapshot before either legacy movement or Stage-2 consumers and before retained mutation. Python numeric sequences and NumPy real scalars / exact numeric ndarray shape (33,3) are normalized to immutable Python floats; ndarray shape and dtype are checked before converting at most 99 values. Object, complex and boolean arrays are refused. Wrong point counts (including 100,000), short points, nonfinite/boolean coordinates or invalid quality are refused as unavailable/invalid_pose_payload; no malformed frame is retained. Hand-built exact PosePayload instances also pass bounded validation before consumers; they cannot bypass the 33-point cap. Quality/visibility rules and distinct unavailable reasons above remain. A coarse absolute coordinate bound of 1,000,000 prevents floating-point overflow; it is a structural payload bound, not a movement threshold or real-coordinate validation. A body-only estimator/movement/extractor/adapter error degrades body output while preserving already computed HB-1 evidence; face/HB-1 failures retain their separate error handling.
- Upload read requests at most 5 MiB + 1 bytes, then rejects excess with HTTP 413. Before Pillow parses JPEG/MPO/PNG metadata, an allocation-light pre-scan allows at most 256 pre-pixel PNG chunks/JPEG markers and 256 KiB of header/metadata bytes; JPEG fill bytes count against the byte budget. Excess or malformed metadata returns 422 before Pillow. The pre-scan rejects JPEG EOI before SOS, preventing Pillow from scanning a later unbounded marker chain; only SOS ends the JPEG scan successfully. It bounds the pre-pixel chunk/marker walk for this policy, rather than guaranteeing elapsed time or bounding all decoder work. Ordinary 5/12 MP JPEG, MPO, progressive JPEG and PNG remain accepted; metadata-heavy files may be refused. The PNG 256-part count includes IHDR and the IDAT iteration: 255 ancillary chunks before IDAT are refused even when tiny (N3, documented boundary retained). Pillow can still inflate compressed PNG metadata within its own 1 MiB per-chunk / 64 MiB total text bounds; this is not a hard time deadline. S46's independent synthetic single-machine probes measured the accepted worst case at about 0.1 s header parsing plus 0.3 s decode; both remain synchronous on the event loop. These are observed timings, not guaranteed ceilings or real-server/load evidence. Pillow then reads headers without loading pixels before OpenCV decoding: at most **12,582,912 pixels (12 MiPixels, about 12.58 MP)** and **8192** in either dimension; this admits 2592x1944, 4000x3000 and 4032x3024 photos under the unchanged 5 MiB compressed limit. MPO is accepted as JPEG-compatible and only the OpenCV-selected first image is decoded. A 4096x4096 PNG (16,777,216 pixels) still exceeds the budget and is rejected before decode; larger declarations are HTTP 413, malformed/unsupported headers HTTP 422. Decoded shape is checked again. Other image formats are rejected. Multipart parsing/spooling can occur before this route: this is not an ASGI/proxy ingress-body cap, a native decoder sandbox or a proof against malformed codec internals.
- Upload waits and CPU slots are separate: at most **four upload reads** per process, each with a **5-second cooperative timeout** (HTTP 408), then at most **two inference/decoder slots** (HTTP 503 on excess). A read holds only an upload slot and a read-only generation snapshot, not a CPU slot or registered admission. Inference slot acquisition precedes header/decode checks; admit() runs only after header validation, successful decode, decoded-size checks and profile validation. Malformed/unsupported/oversized images and invalid profiles never create or refresh generation entries; busy-slot 503 also does not. The pre-upload snapshot remains valid across this entire validation window. Slots release in finally. **Limitations:** CPU inference still runs on the async event-loop thread; no worker offload, per-client quota, native deadline/containment or real-load latency guarantee. Python timeout depends on responsive scheduling/cancellation and is not an ingress or native-IO deadline. Four stalled reads can occupy the upload budget until cancellation completes. Bounded generation-map eviction can still fail closed with 409 under id floods. For an id not registered when its upload started, same-id DELETE invalidates its snapshot; unrelated DELETE does not, unless bounded generation eviction makes history unverifiable. Such 409 refusals are retryable availability loss, not resurrection.
- Internal record/pose builders run outside the store mutation lock; bounded construction does not lock out DELETE or reentrant inspection. Commit checks generation under lock. No client-supplied builder is accepted over HTTP. These are prototype correctness boundaries, not hostile in-process isolation.

## 5a. Pilot measurement code (`socialcue/pilot/`)

**Measurement code only. No capture exists, no pilot has run, and there is no pilot data.** It is the code that would score HB-1 against human annotations of observable behaviour if a consented pilot (gate G5) were ever run under an operator decision and an ethics approval; today it runs on synthetic streams and manufactured annotations only.

- **Annotation schema** (`annotations.py`): a closed record per annotator, participant and 3 s block with the behaviour labels `look_away`, `pause`, `asks_help`, `fidget` (`no_cue` is derived) and three flags. Unknown keys, name/e-mail/face/note/free-text keys and non-int `schema_version` are rejected; tokens are opaque (`ANN-` / `PT-` plus hex). A token's shape cannot prove it is not derived from a person's name.
- **Agreement and scoring** (`agreement.py`, `window_scoring.py`): Cohen's kappa, Krippendorff's alpha and a participant-level bootstrap (seed 505, 1000 draws); HB-1 windows are aligned to annotated blocks (at least 50% overlap) and scored with abstentions counted as failures. The state mapping and thresholds come from the pilot protocol and are hypotheses.
- **Small-N withholding:** below **20 positive windows** (summed over annotators) kappa, alpha and the kappa CI are `None` with reason `fewer_than_20_positive_windows`; only counts and observed agreement are reported. The withheld raw values are kept in memory but are **never written to a report** (JSON or Markdown). A scoring target is evaluable only with at least 10 participants contributing a positive and at least 30 positive windows.
- **Synthetic participant codes:** manufactured participants use the reserved form **`PT-5eed####`** (4 hex digits). Under the synthetic adapter every participant code must have that form, and synthetic codes are refused under a non-synthetic adapter. **This is a code-shape check, not proof:** someone could label real participants `PT-5eed####` and the report would still carry the SYNTHETIC banner (the report also carries a hash of the exact data scored, bound to the provenance manifest, which identifies the data but does not authenticate it). Real pilot codes must never use that prefix.
- **Rights gate:** the `pilot_consented` adapter is a declaration that is `blocked_pending_operator` in the allowlist and also requires an `ethics_approval_token` string. **The token is a declaration, not an approval**: the gate checks that the field exists, nothing verifies that an approval is real, and the allowlist stays blocked until the operator changes it. The gate authorises the adapter's declaration, not the data handed to the scorer.
- **Reports** are labelled `SYNTHETIC / NOT REAL MODEL PERFORMANCE` for synthetic data and `PILOT-DRAFT` otherwise, always with the label-validity caveat, the allowed and disallowed claims and the verbatim limitations ("volunteer sample, scripted mock tasks, small N, single site"). FINAL-opened-once and a frozen protocol hash are not enforced (`final_opened_once_enforced: false`, `protocol_hash: null`); AUROC, ECE and the interaction-log comparator are not implemented.
- **Review:** independent review S16 found the small-N, data-binding and input-guard issues, fixed in commit `a0a2c8d`; review is not validation. The pilot protocol itself lives in the control-room receipts (`receipts\EL-006-socialcue\S9pilot\pilot-protocol.md`), not in this repository.

## 6. Privacy

- **In-memory only.** The session store holds derived face geometry (the largest face's box, five landmarks, expression probabilities, detector confidence, arousal/valence, server time, face count), never an image or video frame. At most **8 sessions x 64 frames**, least recently used evicted, **60 s idle TTL**.
- Expiry is **lazy**: an idle session is logically gone after 60 s and is physically dropped the next time the store is touched (there is no background timer), so idle data is not wiped from process memory until then. Nothing is written to disk by this path (tested with a write spy) [V].
- The session id travels in a header, not the URL. The panel keeps no state in browser storage.
- **Not verified [U]:** retention in server or proxy logs (uvicorn access logs, any reverse proxy) and anything on the operator's machine. The id is a bearer secret and the 8-session cap is global, so any caller could evict other sessions; the backend allows CORS from any origin. This is acceptable only for a single-user local prototype, not a shared service.
- The panel opens its own camera stream separate from the dashboard's webcam; Stop invalidates pending acquisition epochs and releases every currently owned track. A late grant is stopped on arrival and never displayed; Stop does not cancel the browser permission promise itself. These guarantees are tested with fabricated tracks, not a real camera.
